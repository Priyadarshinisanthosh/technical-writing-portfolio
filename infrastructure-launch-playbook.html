Launch Playbook: Isolated CI Runners With Persistent Build Cache

Portfolio simulation: “Forge Runners” is a fictional product. The sample demonstrates how I would coordinate announcement, technical explanation, documentation, demo, and social content for an infrastructure launch.

Product Scenario

Forge Runners schedules ephemeral Firecracker-based CI environments on bare-metal hosts. A Ceph-backed cache persists approved build artifacts across isolated runs. The launch challenge is to explain the value without collapsing three distinct ideas—isolation, compute performance, and cache persistence—into one vague “faster CI” claim.

Launch Asset Matrix

  • Announcement: problem, design decision, evidence, availability, and next step.
  • Docs: quickstart, cache configuration, security model, quotas, invalidation, and troubleshooting.
  • Docs-adjacent explainer: how microVM lifecycle and cache lifecycle differ.
  • Demo: first cold run, second cached run, and proof that workspace state does not persist.
  • Founder brief: five defensible messages, prohibited overclaims, and likely technical questions.
  • Distribution: X thread, LinkedIn post, community Q&A prompt, and customer email.

Sample Announcement

Your runner should be disposable. Your dependencies do not have to be.

Today we are introducing isolated CI runners with persistent build cache. Every job starts in a fresh microVM on dedicated bare-metal capacity. Dependencies selected by your cache policy can be restored independently, so a clean execution environment does not require a cold build every time.

The important boundary is explicit: the workspace is destroyed with the job. Only cache paths configured by the repository are eligible for reuse, and cache keys control when an object can be restored.

- uses: forge/cache@v1
  with:
    path: ~/.cache/gradle
    key: gradle-${{ runner.os }}-${{ hashFiles('**/*.gradle*') }}

Start with the quickstart, then review the cache security model before enabling shared restore keys across branches.

Five-Minute Demo Script

  1. 0:00—Problem: show a cold dependency install dominating the workflow timeline.
  2. 0:40—Configure: add a lockfile-derived cache key and explain invalidation.
  3. 1:40—First run: show a miss, dependency download, and cache save.
  4. 2:40—Second run: show a hit and compare the same job segment.
  5. 3:30—Isolation proof: create an unconfigured workspace file; show that it is absent in the next run.
  6. 4:20—Boundary: explain branch access, cache poisoning controls, size limits, and when not to cache.

Platform-Specific Social Drafts

X thread opener

Fresh CI environments and warm dependency caches are not opposites. The trick is separating the microVM lifecycle from the artifact lifecycle. Here is the architecture—and the security boundary—behind our new runners. 🧵

LinkedIn draft

“Ephemeral” should describe the execution environment, not force every build to download the same unchanged dependencies. Our new runner architecture separates isolated job compute from policy-controlled cache storage. The launch package explains the design, the threat-model boundary, and a benchmark method teams can reproduce.

Community prompt

What is the hardest part of cache reuse in your CI system: invalidation, branch trust, observability, or storage cost? We are publishing our design assumptions and would value counterexamples from teams operating large monorepos.

Launch Readiness Gate

Do not publish until Product, Engineering, Security, Support, and Documentation agree on terminology, availability, limits, failure behavior, benchmark methodology, rollback language, and support ownership. The same facts must appear in the announcement, demo, UI, and docs.
