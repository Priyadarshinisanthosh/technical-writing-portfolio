Azure Web Application Production Recovery Runbook

Portfolio Simulation
This runbook describes a fictional Azure-hosted application. All hostnames, resources, configurations, and procedures are illustrative. The sample demonstrates infrastructure and operational documentation practices without exposing client information.

1. Purpose

Provide a repeatable procedure for diagnosing and recovering a web application when users cannot access the service or when the Azure Application Gateway reports an unhealthy backend.

2. Scope

This runbook covers the following simulated path:

Internet
   |
   v
Azure Application Gateway
   |
   v
Azure Load Balancer
   |
   v
Application VM / Web Service
   |
   v
Database

Covered scenarios include:

  • Application unavailable
  • HTTP 502 Bad Gateway
  • Unhealthy Application Gateway backend
  • Load balancer health-probe failure
  • Application service stopped
  • Network/security rule blocking expected traffic

Database recovery is outside the scope of this sample.

3. Audience

  • IT Operations
  • Cloud Operations
  • Infrastructure Engineers
  • Application Support
  • DevOps / SRE
  • Incident Managers

4. Preconditions and safety controls

Before making a production change:

  1. 1. Confirm an incident/change record exists when required by organizational policy.
  2. 2. Confirm you are working in the correct subscription, resource group, and environment.
  3. 3. Capture the current configuration before modifying it.
  4. 4. Use least-privilege access.
  5. 5. Do not expose secrets, connection strings, tokens, or customer data in incident notes.
  6. 6. Prefer reversible changes.
  7. 7. Escalate rather than bypassing a security control to restore service.

7. Scenario: HTTP 502 from Application Gateway

Symptoms

Users receive:

502 Bad Gateway

Application Gateway may report one or more backend targets as unhealthy.

Likely causes

  • Backend VM unavailable
  • Application service stopped
  • Incorrect backend port
  • Health probe path returns a non-success response
  • Network Security Group (NSG) blocks expected traffic
  • Load balancer/backend configuration mismatch
  • TLS/certificate configuration problem when HTTPS is used to the backend

Diagnostic procedure

Step 1 — Check Application Gateway backend health

Open the Application Gateway resource and inspect Backend health.

Record:

  • Backend target
  • Health state
  • Reported reason
  • Probe protocol
  • Probe port
  • Probe path

Expected: Required backend targets report Healthy.

If healthy, investigate listener/routing/application-level issues before changing backend infrastructure.

Step 2 — Verify VM state

Confirm the application VM is running and has not entered a failed/deallocated state unexpectedly.

Expected: VM state is Running.

If the VM is unavailable, follow the organization's approved VM recovery procedure.

Step 3 — Verify the application service

Connect using the approved administrative method and verify that the application/web service is running and listening on the configured backend port.

Example Windows check:

Get-NetTCPConnection -State Listen

Example Linux check:

ss -lntp

Do not restart the service automatically unless the restart is authorized and the impact is understood.

Step 4 — Test the health endpoint locally

From the backend, test the configured health path.

curl -I http://localhost/health

Expected: The endpoint returns the success status expected by the configured probe.

A 404, 500, authentication challenge, redirect loop, or timeout can cause the backend to be marked unhealthy depending on probe configuration.

Step 5 — Validate the health probe

Compare the approved design with the active probe:

  • Protocol
  • Host
  • Port
  • Path
  • Timeout
  • Interval
  • Unhealthy threshold

Do not change a probe merely to force a Healthy status. Confirm that the probe tests a meaningful application condition.

Step 6 — Validate network rules

Verify that NSG and routing rules allow the intended traffic path between the relevant components.

Check for:

  • Recently changed NSG rules
  • Incorrect source/destination
  • Incorrect port
  • Route-table changes
  • Firewall policy changes

Do not create broad Any/Any allow rules as a troubleshooting shortcut.

Step 7 — Validate load balancer health

If Application Gateway routes through a load balancer in the approved architecture, verify:

  • Backend pool membership
  • Health probe configuration
  • Load-balancing rule
  • Frontend/backend ports
  • VM/NIC association

Step 8 — Retest

After an approved corrective action:

  1. 1. Recheck backend health.
  2. 2. Test the public endpoint.
  3. 3. Validate a representative application transaction.
  4. 4. Review monitoring for continued failures.

Success criteria

Recovery is complete when:

  • Required backend targets report healthy.
  • Public endpoint responds successfully.
  • Representative user workflow succeeds.
  • Error rate returns to normal.
  • No new infrastructure/security alerts indicate a related problem.

8. Recovery actions

Use only the action that addresses the validated cause.

Application service stopped

  1. 1. Capture service state and relevant logs.
  2. 2. Confirm restart authorization.
  3. 3. Start/restart the affected service using the approved platform procedure.
  4. 4. Verify the listening port.
  5. 5. Verify the health endpoint.
  6. 6. Recheck Application Gateway backend health.
  7. 7. Validate the public application.

Incorrect probe configuration

  1. 1. Compare active settings with the approved configuration.
  2. 2. Capture current settings.
  3. 3. Correct only the identified mismatch through the organization's approved change mechanism.
  4. 4. Verify backend health.
  5. 5. Record the change in the incident/change record.

Blocking network rule

  1. 1. Identify the specific rule causing the block.
  2. 2. Validate the required source, destination, protocol, and port.
  3. 3. Use the organization's approved network-change process.
  4. 4. Apply the narrowest permitted correction.
  5. 5. Retest connectivity.
  6. 6. Confirm no unintended exposure was introduced.

9. Rollback

Rollback is required when an approved recovery change:

  • Does not resolve the incident,
  • Introduces a new failure,
  • Creates unacceptable security exposure, or
  • Produces unexpected application behavior.

General rollback procedure:

  1. 1. Stop further changes.
  2. 2. Restore the captured previous configuration using the approved deployment/change method.
  3. 3. Verify the rollback completed.
  4. 4. Recheck service health.
  5. 5. Record the outcome.
  6. 6. Escalate with collected evidence.

11. Evidence collection

Attach or record:

  • Incident timeline
  • Monitoring screenshots or exported evidence as permitted
  • Application Gateway backend-health result
  • Relevant application/service logs
  • VM health
  • Recent deployment/change IDs
  • Network/probe configuration observations
  • Corrective action
  • Validation result

Redact credentials and sensitive data.

12. Post-incident activities

After service restoration:

  1. 1. Confirm monitoring remains stable for the agreed observation period.
  2. 2. Update the incident record.
  3. 3. Document the root cause when established.
  4. 4. Identify corrective/preventive actions.
  5. 5. Update this runbook if the incident exposed a documentation gap.
  6. 6. Link the final post-incident review according to organizational policy.
